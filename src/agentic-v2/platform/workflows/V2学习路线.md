# V2学习路线

`taskType` 固定为 `learning_route`。开始节点三个文本参数必须绑定：`request`、`task_context_json`、`evidence_bundle_json`。

## 输入与版本

- `task_context_json.activeLearningRouteKnown=false` 时，只输出 `needs_input`，要求重新加载当前路线状态；不得猜 `baseRouteVersion`。
- 已确认存在活动路线时，`baseRouteVersion` 必须取该路线的真实版本；首次路线为 `null`。
- `baseVersion` 取当前活动职业计划版本；没有活动计划时为 `null`，不得用 `0` 冒充。
- `weeklyBudgetHours` 取已确认画像预算；未知时输出 `needs_input`，不得自行补 8 小时。

## 规则

1. 每个任务必须写清对象、预计投入、产出和验收标准；缺少任一项时不能生成可确认候选。
2. 每周任务总投入不得超过 `weeklyBudgetHours`；总时长与阶段周期必须能解释。
3. 资源必须有可追溯来源；没有合适资源时给出无外链实践任务，不伪造 URL。
4. 不创建已完成状态、不直接修改 `CareerPlan` 任务或进度。
5. 用户接受后只创建新的 `LearningRoute` 版本；旧路线归档。
6. 缺目标、周期、预算或路线状态时输出 `needs_input`，不得用空数组和占位符填满。

## 周安排的唯一来源

period 使用用户已确认的整数周，例如 4周。用户只提供月份或日期范围且无法明确周数时先补问，不假定每月四周。
stages[].tasks 为唯一任务来源；每项包含唯一 id、整数 weekIndex（从 1 开始）、estimatedHours。跨周任务拆成每周独立子任务。顶层 tasks 省略或为 []；若保留，必须与阶段任务按顺序完全一致，不独立再生成一份。每周 estimatedHours 之和不得超过 weeklyBudgetHours；整个周期总量合格不能替代逐周校验。不要把示例中的 4周、6小时、SQL 或版本当默认用户事实。
